# Задание 4. Ролевой доступ к кластеру Kubernetes

Ролевая модель доступа к кластеру PropDevelopment, где развёрнуто большинство бизнес-сервисов компании. Модель продолжает решения первых трёх заданий: пространства имён повторяют доменную структуру компании, а привилегированные действия отделены от повседневных так же, как это описано в [проверочном листе](../Task2/IB.md).

## Состав директории

| Файл | Пункт задания | Содержание |
| --- | --- | --- |
| [`01-create-users.sh`](./01-create-users.sh) | 3 | Создание пользователей: выпуск клиентских сертификатов X.509 и сборка kubeconfig |
| [`02-create-roles.sh`](./02-create-roles.sh) | 4 | Создание пространств имён, кластерных ролей и ролей в пространствах имён |

## Как запустить

```bash
minikube start --driver=docker
```

```bash
cd Task4 && ./01-create-users.sh && ./02-create-roles.sh && ./03-bind-roles.sh
```

Скрипты идемпотентны — повторный запуск не ломает состояние. Все три проверяют, что текущий контекст `kubectl` указывает именно на minikube: рядом часто настроен рабочий кластер, а скрипты создают пространства имён и права доступа. Проверка снимается явно через `EXPECTED_CONTEXT=<имя> ./<скрипт>`.

## 1. Как построена модель

Права разделены по двум независимым измерениям.

**По вертикали — уровень полномочий.** Просмотр → настройка кластера → привилегированные действия. Пользователь поднимается на следующий уровень только тогда, когда это нужно для работы, и никогда «заодно».

**По горизонтали — организационная структура.** Каждый домен компании получает своё пространство имён, и права разработчиков действуют только внутри него. Разработчик домена «Продажи» не имеет доступа к сервисам ЖКУ и финансов — это то самое разграничение по оргструктуре, отсутствие которого в Задании 2 зафиксировано как критичный вопрос 1.7.

**Ключевое свойство RBAC, на котором построена защита:** в Kubernetes нет запрещающих правил. Доступ определяется не тем, что запрещено, а тем, что в роль **не включено**. Поэтому `secrets` и `pods/exec` намеренно отсутствуют во всех ролях, кроме двух привилегированных, — и это не оговорка, а сам механизм защиты.

### Пространства имён

| Пространство имён | Домен компании | Класс данных (Задание 1) |
| --- | --- | --- |
| `sales` | Группа сервисов для клиентов: `client-mart-app`, `client-crm-app`, `client-tour-app`, `client-mart-estate-app` | Конфиденциальные |
| `utility` | Группа сервисов ЖКУ: `tenant-core-app`, CRM собственников | Конфиденциальные |
| `smart-access` | Группа сервисов умного доступа из Задания 3: `smart-access-app`, `partner-adapter`, `consent-service` | Конфиденциальные |
| `finance` | Домен «Финансы»: `accountant-service-1` | Конфиденциальные |
| `data-platform` | Домен «Дата»: хранилище, BI, отчётность | Внутренние |
| `platform` | Общие пограничные сервисы: `api-gateway`, `auth-service-1`, `secrets-vault` | Секретные |

Класс данных проставляется меткой `data-classification` при создании пространства имён — классификация из Задания 1 переносится в кластер машиночитаемо и в дальнейшем может использоваться политиками допуска.

## 2. Таблица ролей

| Роль | Права роли | Группы пользователей |
| --- | --- | --- |
| **`cluster-viewer`**<br>*ClusterRole* | `get`, `list`, `watch` на рабочие нагрузки, сервисы, конфигурации, узлы, события и метрики во всём кластере. **Секретов в правилах нет** — просмотр `secrets` невозможен. Изменять ничего не может | `viewers` — бизнес-аналитики, менеджеры, аналитики BI<br>`auditors` — внешние аудиторы на время комплексного аудита |
| **`cluster-configurator`**<br>*ClusterRole* | Полный цикл (`create`, `update`, `patch`, `delete`) над настройками кластера: пространства имён, узлы, квоты и лимиты, классы хранения и ingress, классы приоритета, CRD, вебхуки допуска. Рабочие нагрузки — **только чтение**. **Без секретов и без управления RBAC** | `platform-ops` — инженеры эксплуатации платформы |
| **`cluster-security-admin`**<br>*ClusterRole* | Полный цикл над `roles`, `rolebindings`, `clusterroles`, `clusterrolebindings`, сетевыми политиками и запросами на подпись сертификатов. Просмотр событий и состояния кластера. **Чтения секретов не имеет** | `security` — специалист по информационной безопасности и его резерв |
| **`namespace-developer`**<br>*Role, своя в каждом пространстве имён* | Полный цикл над сервисами своего домена: поды, деплойменты, statefulset'ы, задания, сервисы, ingress, конфигурации, автомасштабирование, чтение журналов. **Без `secrets` и без `pods/exec`.** Действует только в своём пространстве имён | `dev-sales`, `dev-utility`, `dev-smart-access`, `dev-finance`, `dev-data`, `dev-platform` — разработчики и DevOps-инженеры продуктовых команд соответствующих доменов |
| **`secret-reader`**<br>*ClusterRole, выдаётся только через RoleBinding* | **Привилегированная.** `get`, `list`, `watch` над `secrets`. Кластерной привязки не имеет ни одной — выдаётся точечно в конкретном пространстве имён | `sre-oncall` — дежурная смена эксплуатации |
| **`pod-debugger`**<br>*ClusterRole, выдаётся только через RoleBinding* | **Привилегированная.** `pods/exec`, `pods/attach`, `pods/portforward` и чтение журналов. Вход в контейнер даёт доступ к смонтированным секретам и данным в памяти в обход просмотра объекта `Secret` | `sre-oncall` — дежурная смена эксплуатации |
| **`cluster-admin`**<br>*встроенная ClusterRole* | Полные права на кластер | **Группам не выдаётся.** Остаётся персонально у двух инженеров как аварийный доступ; выдача фиксируется и разбирается после использования |

## 3. Пользователи для демонстрации

Скрипт `01-create-users.sh` создаёт семь пользователей — по одному на каждый уровень модели, чтобы разграничение можно было проверить вживую:

| Пользователь | Группа | Роль в компании |
| --- | --- | --- |
| `anna.ivanova` | `viewers` | Бизнес-аналитик |
| `igor.orlov` | `auditors` | Внешний аудитор |
| `pavel.smirnov` | `dev-sales` | Разработчик домена «Продажи» |
| `olga.petrova` | `dev-smart-access` | Разработчик домена «Умный доступ» |
| `sergey.volkov` | `platform-ops` | Инженер эксплуатации |
| `marina.orlova` | `security` | Специалист по информационной безопасности |
| `denis.kuznetsov` | `sre-oncall` | Дежурный SRE, привилегированный доступ |

Права привязаны к **группам**, а не к людям: группа берётся из поля `O` сертификата. Приём или уход сотрудника не требует правки RBAC — меняется только сертификат. Группы, для которых пользователи не заведены (`dev-utility`, `dev-finance`, `dev-data`, `dev-platform`), существуют в привязках и начнут действовать при выдаче первого сертификата.

## 4. Принятые решения

**Пользователь в Kubernetes — не объект API.** Кластер не хранит учётные записи людей: он узнаёт пользователя из клиентского сертификата, где `CN` — имя, а `O` — группа. Поэтому «создание пользователя» сводится к выпуску сертификата, подписанного центром сертификации кластера, и сборке kubeconfig. Сертификаты выпускаются на 90 дней — ограниченный срок вместо бессрочного доступа закрывает вопрос 2.3 проверочного листа о ротации.

**Информационная безопасность управляет правами, но не читает секреты.** Разделение обязанностей: `cluster-security-admin` может выдать и отозвать любое право, но не может посмотреть содержимое `Secret`. Это не формальность — Kubernetes не позволит обладателю этой роли выдать себе доступ к секретам: RBAC запрещает создавать привязки с правами, которых у создателя нет (privilege escalation prevention). Обойти разделение можно только через `cluster-admin`, а он не выдаётся группам.

**Эксплуатация настраивает кластер, но не трогает приложения.** У `cluster-configurator` рабочие нагрузки доступны только на чтение. Настройка платформы не означает права менять чужие сервисы: за сервис отвечает продуктовая команда домена.

**Вход в контейнер — привилегия того же уровня, что и чтение секретов.** `pods/exec` часто оставляют разработчикам как удобство, но зайдя в контейнер, можно прочитать смонтированные секреты и данные в памяти в обход всех ограничений на объект `Secret`. Поэтому `pod-debugger` вынесен в отдельную привилегированную роль рядом с `secret-reader`.

**Привилегированные роли не имеют кластерных привязок.** `secret-reader` и `pod-debugger` объявлены как `ClusterRole`, но привязываются исключительно через `RoleBinding` в конкретном пространстве имён. Это позволяет переиспользовать одно определение роли и при этом не создавать ни одного носителя права «читать все секреты кластера».

**Закрытые ключи не попадают в репозиторий.** Каталоги `.pki/` и `kubeconfig/` исключены через `.gitignore`. В продуктивной среде ключ генерируется на стороне владельца, наружу отдаётся только запрос на подпись — здесь ключи создаются локально ради воспроизводимости демонстрации.

## 5. Проверка

`03-bind-roles.sh` завершается автоматической проверкой: 18 сценариев через `kubectl auth can-i` с подстановкой группы. Проверяется не только то, что разрешено, но и то, что **должно быть запрещено** — отсутствие доступа к секретам, к чужому домену и к `pods/exec`.

Проверка от имени реального пользователя, с его сертификатом:

```bash
kubectl --kubeconfig=./kubeconfig/pavel.smirnov.kubeconfig get pods -n sales
```

```bash
kubectl --kubeconfig=./kubeconfig/pavel.smirnov.kubeconfig get pods -n finance
```

Первая команда отработает, вторая вернёт отказ — разработчик домена «Продажи» не видит финансовый домен.

### Результат прогона на minikube

Модель проверена на пустом кластере minikube (Kubernetes v1.35.1). Все 18 проверок `03-bind-roles.sh` пройдены. Дополнительно проверено обращение настоящими сертификатами пользователей — не подстановкой групп, а реальным клиентским сертификатом:

| Пользователь | Группа | Команда | Результат |
| --- | --- | --- | --- |
| `anna.ivanova` | `viewers` | `get pods -A` | доступ |
| `anna.ivanova` | `viewers` | `get secrets -n sales` | **отказ** |
| `pavel.smirnov` | `dev-sales` | `get deployments -n sales` | доступ |
| `pavel.smirnov` | `dev-sales` | `get pods -n finance` | **отказ** |
| `pavel.smirnov` | `dev-sales` | `get secrets -n sales` | **отказ** |
| `olga.petrova` | `dev-smart-access` | `get deployments -n smart-access` | доступ |
| `olga.petrova` | `dev-smart-access` | `get deployments -n sales` | **отказ** |
| `sergey.volkov` | `platform-ops` | `get storageclass` | доступ |
| `sergey.volkov` | `platform-ops` | `get secrets -n platform` | **отказ** |
| `marina.orlova` | `security` | `get rolebindings -n sales` | доступ |
| `marina.orlova` | `security` | `get secrets -n platform` | **отказ** |
| `denis.kuznetsov` | `sre-oncall` | `get secrets -n platform` | доступ |
| `denis.kuznetsov` | `sre-oncall` | `get nodes` | **отказ** |

Проверка личности, которую видит кластер:

```bash
kubectl --kubeconfig=./kubeconfig/pavel.smirnov.kubeconfig auth whoami
```

Возвращает `Username: pavel.smirnov`, `Groups: [dev-sales system:authenticated]` — имя из поля `CN` сертификата, группа из поля `O`.

### Замечание о проверке подресурсов

`kubectl auth can-i create pods/exec` проверяет **не то, что кажется**: запись `pods/exec` трактуется как `ТИП/ИМЯ`, то есть как под с именем `exec`. Такая проверка показывает наличие права `create pods` и не касается входа в контейнер. Подресурс проверяется отдельным флагом:

```bash
kubectl auth can-i create pods --subresource=exec -n sales --as=probe --as-group=dev-sales
```

В `03-bind-roles.sh` используется именно этот вариант — иначе проверка привилегированного доступа даёт ложный результат в обе стороны.
