# Задание 5. Управление трафиком внутри кластера Kubernetes

Разграничение сетевого трафика между четырьмя сервисами в одном пространстве имён: пользовательский контур (`front-end` ↔ `back-end-api`) изолирован от административного (`admin-front-end` ↔ `admin-back-end-api`).

## Состав директории

| Файл | Содержание |
| --- | --- |
| [`00-default-deny.yaml`](./00-default-deny.yaml) | Базовый запрет всего трафика и точечное разрешение DNS |
| [`non-admin-api-allow.yaml`](./non-admin-api-allow.yaml) | Разрешения для пары `front-end` ↔ `back-end-api` |
| [`admin-api-allow.yaml`](./admin-api-allow.yaml) | Разрешения для пары `admin-front-end` ↔ `admin-back-end-api` |
| [`deploy.sh`](./deploy.sh) | Пространство имён, четыре сервиса с метками, применение политик |
| [`verify.sh`](./verify.sh) | Проверка: полная матрица 4×4 и поведение постороннего пода |

Пространство имён `traffic-demo` зафиксировано в `metadata` каждого манифеста, а не вынесено в переменную окружения. Так файл политики можно применить и напрямую, как описано в задании, — он сам знает, куда встаёт:

```bash
kubectl apply -f non-admin-api-allow.yaml
```

По той же причине `deploy.sh` не передаёт ключ `-n` при применении политик: источник истины один — сам манифест.

`deploy.sh` сверяет фактическое состояние с желаемым, а не наличие объектов по имени. Под с нужным именем ещё ничего не гарантирует: сервис мог быть удалён, метка `role` изменена вручную, образ подменён, под завершиться. При любом таком расхождении пара «под + сервис» пересоздаётся, а причина выводится в отчёте:

```
back-end-api-app       метка role=back-end-api       пересоздаю (нет сервиса)
admin-front-end-app    метка role=admin-front-end    пересоздаю (метка role=front-end вместо admin-front-end)
```

## Как запустить

```bash
minikube start --driver=docker --cni=calico
```

```bash
cd Task5 && ./deploy.sh && ./verify.sh
```

## 1. Важное условие: CNI должен уметь применять политики

**Стандартный сетевой драйвер minikube не применяет NetworkPolicy.** Объекты создадутся, `kubectl get networkpolicy` покажет их как существующие — и весь трафик при этом останется открытым. Молчаливо: ни ошибки, ни предупреждения.

Сама по себе NetworkPolicy — это только декларация намерения. Исполняет её сетевой драйвер (CNI), и не каждый драйвер умеет это делать. Поэтому кластер поднимается с `--cni=calico`, а `deploy.sh` предупреждает, если Calico в кластере не найден.

Это же и есть главный практический вывод задания: **проверять нужно фактическое поведение сети, а не наличие объектов политики.** Именно поэтому в `verify.sh` каждое правило подтверждается настоящим сетевым запросом.

## 2. Схема разграничения

```
     пользовательский контур              административный контур
   ┌───────────────────────────┐        ┌─────────────────────────────────┐
   │  front-end  ◄────────►  back-end-api    admin-front-end ◄──────► admin-back-end-api
   └───────────────────────────┘        └─────────────────────────────────┘
                    ╲                                    ╱
                     ╲──────────  трафика нет  ─────────╱

   любой посторонний под (без меток)  ──►  трафика нет ни к одному сервису
```

Четыре сервиса развёрнуты из образа nginx в одном пространстве имён `traffic-demo` и различаются **только меткой `role`**. Разграничение построено на метках, а не на именах подов и не на IP-адресах: под, получивший метку `role=front-end`, автоматически получает и права этой роли, независимо от того, как он называется. Это проверяется отдельным тестом в `verify.sh`.

Используется образ `nginx:alpine` — это тот же nginx, но вариант на alpine содержит `wget`, что позволяет проверять связность прямо из сервисов, без вспомогательных подов.

## 3. Как устроены политики

**Сначала полный запрет, потом точечные разрешения.** NetworkPolicy работает только на разрешение — запрещающих правил в ней нет. Пока под не выбран ни одной политикой, он открыт для всех. Изоляция появляется в момент, когда под попадает под действие хотя бы одной политики: с этого момента разрешено только то, что перечислено явно. Поэтому `default-deny-all` с пустым `podSelector: {}` и пустым списком правил закрывает все поды пространства имён, а `non-admin-api-allow.yaml` и `admin-api-allow.yaml` открывают ровно нужные направления.

**Правила симметричны.** Для каждой пары открыты обе половины: `Ingress` на стороне получателя и `Egress` на стороне инициатора. Одной половины недостаточно — базовый запрет закрывает оба направления, и пакет должен быть разрешён и на выходе из пода-источника, и на входе в под-получатель.

**DNS разрешён отдельно.** Как только на под действует политика с `Egress`, закрывается и обращение к CoreDNS. Без исключения `allow-dns-egress` запрос по имени сервиса падал бы на разрешении имени (`bad address`), а не на сетевой политике — и проверка показывала бы правильный результат по неправильной причине. Разрешение выдано минимальное: только порты 53 UDP и TCP и только к подам `k8s-app=kube-dns` в `kube-system`.

**Ограничение по портам.** Все разрешения выданы на TCP/80, а не на весь диапазон: политика описывает конкретный протокол взаимодействия, а не «доступ вообще».

## 4. Результат проверки

Прогон на minikube с Calico, Kubernetes v1.35.1.

```
ИСТОЧНИК \ НАЗНАЧЕНИЕ  front-end  back-end-api  admin-front-end  admin-back-end-api
front-end              разрешено  разрешено     запрещено        запрещено
back-end-api           разрешено  разрешено     запрещено        запрещено
admin-front-end        запрещено  запрещено     разрешено        разрешено
admin-back-end-api     запрещено  запрещено     разрешено        разрешено
```

Между контурами трафика нет ни в одном из восьми направлений.

| Проверка | Результат |
| --- | --- |
| Посторонний под без меток → все четыре сервиса | запрещено во всех четырёх случаях |
| Посторонний под с меткой `role=front-end` → `back-end-api` | разрешено |
| Посторонний под с меткой `role=front-end` → `admin-back-end-api` | запрещено |

Последние две строки показывают, что политика привязана к роли, а не к личности пода: посторонний под получает ровно те права, которые даёт его метка.

### О диагонали матрицы

Обращение пода к самому себе разрешено, хотя `Egress` открыт только на партнёра по паре. Это не пробел в политике: **NetworkPolicy не применяется к трафику, у которого источник и получатель — один и тот же под.** Запретить поду обращаться к самому себе сетевой политикой невозможно ни в Calico, ни в любой другой реализации. В `verify.sh` это учтено в ожидаемой матрице явно.

## 5. Проверка вручную

Способ из задания — посторонний под, у которого нет меток и, следовательно, никаких разрешений:

```bash
kubectl run test-$RANDOM --rm -i -t -n traffic-demo --image=alpine -- sh
```

Внутри пода обращение к любому из четырёх сервисов завершается таймаутом:

```bash
wget -qO- --timeout=2 http://back-end-api-app
```

Проверка разрешённого направления — из самого сервиса, а не из постороннего пода:

```bash
kubectl exec -n traffic-demo front-end-app -- wget -qO- -T 3 http://back-end-api-app
```

Проверка запрещённого направления (завершится таймаутом):

```bash
kubectl exec -n traffic-demo front-end-app -- wget -qO- -T 3 http://admin-back-end-api-app
```

Таймаут задаётся ключом `-T`: это канонический ключ BusyBox wget, который используется в alpine-образах. Длинный вариант `--timeout` здесь работает, но поддерживается не во всех сборках BusyBox, а его отсутствие выглядело бы как срабатывание сетевой политики, хотя на деле это ошибка разбора аргументов.

## 7. Замечание о корпоративной сети

При проверке на этой машине образы Calico не скачивались изнутри кластера: `quay.io` и `registry.k8s.io` за корпоративным прокси отдают сертификат неизвестного удостоверяющего центра, и узел получает `x509: certificate signed by unknown authority`. Docker Hub при этом доступен. Обход, если столкнётесь с тем же:

```bash
for i in cni node kube-controllers; do docker pull calico/$i:v3.31.3 && docker tag calico/$i:v3.31.3 quay.io/calico/$i:v3.31.3 && minikube image load quay.io/calico/$i:v3.31.3; done
```

После загрузки образов достаточно пересоздать поды Calico: `kubectl delete pod -n kube-system -l k8s-app=calico-node`.

## 8. Как проверялась сама проверка

`verify.sh` должен падать не только тогда, когда что-то не работает, но и тогда, когда разрешено лишнее. Это проверено отдельно: во время прогона в кластер временно добавлялась пара политик, открывающих `front-end` → `admin-back-end-api`, то есть ровно то направление, которого быть не должно.

```
ИСТОЧНИК \ НАЗНАЧЕНИЕ  front-end  back-end-api  admin-front-end  admin-back-end-api
front-end              разрешено  разрешено     запрещено        ! yes (ждали no)
```

Скрипт пометил ячейку и завершился с кодом 1. После удаления временных политик — снова код 0. Без такой проверки нельзя утверждать, что зелёный результат что-то значит.
